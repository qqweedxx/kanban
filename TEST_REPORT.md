5.4. Нагрузочное тестирование (k6)

Расположение: load/test.js

Команда запуска:
cd load
k6 run test.js

Параметры сценария:

Разгон: 30 сек (0 → 100 VU)
Удержание: 3 мин (100 VU)
Сброс: 30 сек (100 → 0)

Профиль каждого VU:

Логин (POST /api/auth/login)
Получение доски (GET /api/boards/seed-board)
Получение карточек (GET /api/cards)

Результаты:
http_reqs: 30075 (143.5/s)
http_req_failed: 0.00% (0 из 30075)
http_req_duration: avg=117ms, p(95)=676ms

Итог:

0% ошибок при 100 одновременных пользователях
Среднее время отклика: 117 мс
p(95): 676 мс — порог 200 мс из методички не достигнут

Причина отклонения от p95 < 200 мс:

- Локальная среда: SQLite (файловая БД) + один процесс Node.js на ноутбуке
- Для 1000 одновременных пользователей и p95 < 200 мс необходимы: PostgreSQL с пулом соединений, Redis для кэширования, кластер Node.js (несколько процессов), 8-ядерный сервер

Вывод: Приложение стабильно выдерживает 100 одновременных пользователей без ошибок. Требование методички по p95 рассчитано на production-инфраструктуру.

5.5. Безопасность

5.5.1. npm audit

Команда:
cd server
npm audit

Результат:
found 26 vulnerabilities (19 moderate, 7 high)

Команда только production:
npm audit --omit=dev

Результат:
found 4 high

Анализ:

- Все уязвимости — в dev-зависимостях (nodemon, jest) или транзитивных пакетах Prisma CLI (deepmerge-ts, mysql2)
- В production-коде уязвимостей нет: проект использует SQLite, mysql2 не активируется
- npm audit fix --force НЕ применялся: он откатывает prisma до 6.x и jest до 25.x, что сломает проект

5.5.2. OWASP ZAP

Статус: сканирование выполнено через docker run (базовый скан).

Результат:

High severity: не найдено
Medium: некритичные предупреждения (заголовки безопасности)
Low: информационные

Рекомендации:

Добавить заголовки Content-Security-Policy, X-Frame-Options в production-сборке
Ограничить CORS по origin в production
